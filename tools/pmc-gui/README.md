# Control test GUI

`pmc_gui.py` is a small web server on a PC that talks to the board's text port (TCP 8888), and to a Lake Shore 336 (TCP 7777) when one is given, and serves one page to a browser. It holds the board's one connection, so every tool for the running board is on that page.

## The page

Screenshots on the simulator (GUI build 425, firmware 0.16.9): [Live, during an autotune](screens/live-autotune-running.png) and [Gains, after it](screens/gains-autotune-done.png) and [its log card](screens/gains-autotune-log.png); [the predicted line during a check](screens/live-autotune-predicted.png).

- **Top bar**, on every tab: the GUI's build (commits on its branch, the commit, the commit time; "edited" when its files differ from that commit) and the board's firmware version, the tabs, then three status lights and the board's mode. The build line is printed in the console window at start too.
  - Board: connected, or why there is no link.
  - Lake Shore: the temperatures, off, or why there is no link.
  - Logger: the rows written so far (red dot while it records), or Not logging.
- **Run bar**, under it: the autotune while it runs.
  - Its steps, one per setpoint and the PID table sets: done (with the result, such as KP and TI, and how long it took), in progress, still to do, skipped, stopped.
  - The stage it is in, how long it has been in it and the most it can take.
  - Elapsed time, time left (about), the clock time it should finish, a progress bar, and the folder it saves to.
  - Stop autotune. When nothing runs, it shows how the last autotune ended.
- **Readings and charts**, on every tab: pressure, setpoint and valve, and each 336 input by name. The pressure chart (pressure and setpoint) marks where each autotune stage starts; the valve has its own chart and scale under it, so a move of a few tenths of a percent shows. Each temperature has its own strip and scale under it, so a few mK of change shows. 5 min to 4 hours. Each line shows its one-minute average rate of change (the slope of a straight line through the last 60 s of samples, per minute) in the legend or the chart title.
  - Predicted, while the autotune runs a check step: a dashed purple line on the pressure chart and on the valve chart, running ahead of a grey "now" line to where the step should settle (the chart's time axis stretches to show it). It is the board's PI (KP and TI under test, the same sums, anti-windup and travel limits, the valve's speed taken as 0.4 % a second) run on the fitted response of this setpoint, from the pressure and valve at the step. It has no deadband, reversal hold or needle stick, so the real line wanders round it by about the noise. The fit is the learned one for the setpoint, else the reach, the noise hold and the relay test fitted as one series (the reach has the slow part of the answer, the relay the fast part), which is rough (on the simulator 14 to 35 % of the step RMS); from the second check on, the line is refitted to the check before as it ran, the board's PI included, which on the simulator brings it within about 8 % of the step. Steps already run keep their predicted line, cut where the step ended, so the two can be compared; with no usable fit there is no line. The legend names the step, the gains and the fit (K, L, tau) the line was worked out on; the predicted overshoot, settle time, t63 and t90 are in the Working card and the log.
- **Valve from KP, TI**, in AUTO: how much of the valve opening is the KP part, KP x (setpoint - pressure), and how much the TI part (the integral, the rest of the valve), from the gains in use and the samples. Under it, how far the valve moved in the last minute and how much of that each part did (the TI part moves KP x error / TI per minute). The board does not send its own P and I, so these are worked out on the PC; the deadband, travel limits and the switch can make the two parts add up to a little more or less than the valve moved.
- **STOP**, on every tab: the valve stops where it is and the autotune ends, with nothing put back. Stop autotune, by contrast, puts back the setpoint, mode and PID table the autotune found.
- **Every button says what happened**: it flashes green or red, and a line at the bottom of the page names the action and the board's answer. The mode buttons show the board's state, filled when on. A PID box changed but not yet sent has an amber edge. While the autotune runs, its card is outlined and marked Running and Run autotune is greyed.

The tabs:

- **Live**: mode (AUTO / MANUAL), setpoint, Go to %; the PID gains in use (`PID?`) and Set and save (`PID SET`, firmware 0.15.8 and later); the logger; the Lake Shore 336 connection; the activity log.
- **Gains**: the autotune for the board's PID table, from `tools/gain-schedule/pmc_autotune.py` (its README has the rules and numbers). Firmware 0.15.15 and later has its own gain schedule, the PID table (three PID sets, Menu > PID tuning > PID table); while it is on, the PID box line names the set in use. The autotune finds the three sets by experiment, as an industrial autotuner does.
  - Before it starts it checks that the valve is homed, there is no fault and Remote control is On. Start it with AUTO holding a mid setpoint. Setpoints are 2 4 8 12 16 24 48 mbar unless changed (1 mbar sits below the valve's knee and its gains are far too high for the setpoints above it). They run in the order typed, so "24 16 12 8 4 2" tests on the way down. Coming down from a high flow the heat exchanger starts cold, so below about 8 mbar the pressure is steeper with valve and answers faster for the first 10 to 20 min; a run down may find a lower KP and shorter TI there. Learned gains are kept per setpoint, not per direction: a run down replaces the run up's rows (each run's own results.csv keeps them). Then, at each setpoint in turn:
    1. AUTO at the setpoint until it holds (10 minutes at most): the last minute's mean within 5 % of it, the last 30 s within 2.5 % and level, with the First gains at the first setpoint (KP 0.10, TI 0.40 unless changed) and the gains found at the setpoint before for each later one. The valve position it holds at is x0.
    2. Relay test, in MANUAL: the valve goes to x0 + d while the pressure is below the setpoint and x0 - d while it is above, so the loop oscillates by itself. The size of that oscillation gives the ultimate gain Ku (the KP at which AUTO would just oscillate) and its period Pu. d starts at the Relay step box for the first setpoint, then from the Ku before; it doubles when nothing crosses for 90 s (after first moving x0 by d, in case x0 was off) and halves when the swing passes 15 % of the setpoint. If the pressure runs off (over twice the setpoint, or under 40 % of it) d drops to a quarter and the test starts again once the pressure is back (2 minutes at most); only at the least d (0.1 %) is the setpoint skipped. It ends after two steady cycles, or 12 minutes.
    3. First gains. With a fit of the response learned at this setpoint (K in mbar per %, dead time L, lag tau): L_eff = max(L, Pu / 4); TI = min(max(tau, 2.5 L_eff), 20 L_eff); KP = min(TI / (5 K L_eff), Ku / 3); KD 0. With no fit yet: KP = Ku / 4 and TI = 2 Pu. They are used for the first check only.
    4. Check, in AUTO with those gains: a hold, then the setpoint 20 % up and back. After every check the pressure is fitted to the valve over the check's samples (`p = c + drift x t + K x lag_tau(valve(t - L))`, a grid of L and tau, kept when R2 is 0.8 or more, K above 0 and the valve moved over 0.05 %), and the check is measured on each leg: overshoot and reversals, the seconds to 63 % and 90 % of the step, how far the valve backs off before 90 % (% of its move), and the sag (the longest time under the setpoint with the valve not moving). The first rule that applies is applied, and the check is run again: more than 2 reversals or a watchdog cut, KP x 0.7; overshoot over 5 % of the step, KP x 0.8; a tail (no overshoot, t90 over 4 x t63, valve backing off over 10 %), TI x 0.7; slow (no overshoot or back-off, t90 over 8 x (L_eff + tau)), TI x 0.8; otherwise it passes. TI never goes under 2.5 L_eff or the integral gain over 1 / (4 K L_eff): there the check passes with the note "as fast as the cryostat allows". These rules never raise KP, and never take it over Ku / 3. When no KP cut is due, the check is also fitted as it ran and KP and TI are searched on three models of that fit (the fastest worst settle with no model over 5 % overshoot, KP up to Ku / 2 and never back over a cut); those gains are used when they settle in 0.75 times the check's time or less and differ by more than 15 %, so KP can go up as well as down. At most 4 refinements; one that makes the check worse is undone and ends them. A check step up that cannot be reached (the valve over 90 % for 30 s short of the band, or the pressure no longer rising at the end with the valve opened 15 % more) ends the check, and that setpoint is skipped and left out of the sets. The pressure's own wander, measured with the valve held before the relay test, is allowed for: overshoot counts only beyond it (a quarter of the step at most), and it widens the settling band.

    Learned gains: every setpoint's result (KP, TI, Ku, Pu, the changes, and the fit it ended on with the last check's t63, t90 and back-off) is kept in `autotune-learned.csv` in the log folder, newest per setpoint. With Start from Learned gains (the default) a setpoint learned before reaches with its own learned gains, sizes its relay step from its own Ku and, when the row has a fit, starts the check from the first-gains rule on that fit. A learned file from before the fit loads with those columns empty; such a setpoint starts from Ku / 4 and 2 Pu. If the new relay test's Ku is more than 2 times off the learned one the plant has changed and that setpoint starts fresh. Start from Fresh ignores the file (its results still go in it). The first time, with no learned file yet, it is built from the `results.csv` of the earlier autotune runs in the same log folder. The card lists what is learned.

    Whenever AUTO runs (reaching and holding a setpoint, the check steps) a watchdog watches for AUTO oscillating hard: four swings in a row within 400 s, each more than 30 % of the setpoint (0.2 mbar at least). It then cuts KP at once with `PID SET`, by half, or to a quarter when the swing is bigger than the setpoint itself, and goes on with the lower gain, and the wait for AUTO to hold starts again (the stage line shows the new KP and its own time limit); a check step that oscillated is tried again with KP cut.

    Firmware before 0.16.9 holds the valve for a fixed 0.10 % on every reversal; on small steps that lets the pressure sag under the setpoint, which reads as overshoot and cuts KP more than it needs. Run the autotune on 0.16.9 or later, where the hold scales with KP; on an older version the Working card says so at the start.

    A setpoint that cannot be reached, gives no usable oscillation, or where the board leaves AUTO (a warning) is skipped; a fault ends the run. 15 to 35 minutes a setpoint (the longer with refinements), so 2 to 4 hours for eight. While it runs the PID table is Off and set 1 holds the gains under test (`PID SET`); at the end set 1, the PID table, the setpoint and the mode are put back as found.

    The Working card at the top of the Gains tab shows the sums as they are done, under a heading for each setpoint: x0, the noise and switch band, each relay cycle, Ku and Pu with the numbers that went in, the first gains, each check step with its figures, the fit after each check and the rule it triggered, any watchdog cut, and the result. A line above it shows the stage running now (time so far, pressure, watchdog count) and, in AUTO, the valve split into its KP and TI parts. Under the PID table, each set's working is written out.

    The Log card under it lists, newest first, every decision (learned or fresh, the first gains, each rule and why, an undone refinement, a watchdog cut, a relay step change, a skipped setpoint, the result), every change the autotune makes to KP, TI and KD on the board (old -> new, and why), and the setpoint, mode and valve commands it sends, each with the KP, TI and KD in force after it. Download log saves the run's `autotune_log.csv`, which has the same rows plus every calculation in the Working card.

    The results fill in as each setpoint finishes: per setpoint Ku, Pu, the relay step, KP, TI, the fit, t63 and t90, the back-off, the sag and the check (with any changes), and the three PID table sets. Each set takes the lowest KP and the geometric mean of the TIs of the setpoints in its band (below B1, B1 to B2, above B2; 6 and 14 mbar with hysteresis 10 % unless changed). A band with no setpoint measured keeps the board's set. Write to board sends `PIDS SET 1` to `3` and `SCHED SET PV,<B1>,<B2>,<H>`, which turns the PID table on; nothing is written before that. The relay sees the valve as it is at that setpoint, needle stiction included.
- **Board**: the board's identity, Reset faults and OK warning, the event log (`EVNT?`), the board clock set to the PC's time (`TIME SET`), and a command line for any text-port command.

The autotune's relay test, fit, rules and sets, and the text-port link, are in `pmc_autotune.py`, imported from there.

Not on the page: the firmware's own checks (`simulator/tests`, `tools/*-test`, `tools/xbuild`, `tools/ui-preview`). They build the firmware with a compiler or the simulator with Node and never talk to a board.

## What is saved

Everything is written as it happens, each row flushed to disk, in `pmc-logs` in the folder the GUI is started from (`--log-dir` to change it; the Logger box shows the full path).

- `pmc_<date>_<time>.csv`, the logger: every sample, one a second, with the PC time, the setpoint, pressure, valve, mode, alarms, the test stage, and each 336 input in K (`A_heat_exchanger_K`, `D_cold_head_K`). It records whether or not a test runs, and keeps recording the temperatures when the board's link is down. Stop logging, Start logging and New file split it; a new file also starts when the 336 inputs change.
- One folder per autotune, `autotune_<date>_<time>`:
  - `samples.csv`: the samples while it ran, as in the logger.
  - `messages.txt`: every message it gave, with the time.
  - `autotune_log.csv`, the autotune's log: one row per calculation, decision, gain change and command, as it happens. Columns: `time` (PC), `t_s` (seconds since the start, board time), `setpoint_mbar` (the setpoint being tuned), `stage` (as marked on the chart), `kind` (`start`, `calc`, `decision`, `gains`, `command`, `result`, `end`), `kp`, `ti_min`, `kd` (on the board after the row: the autotune always sets KD 0), `change` (on a `gains` row, what changed, for example `KP 0.64 -> 0.45`) and `text` (the line itself, and for a command or a change of gains, why). The `start` row has the settings and what it found on the board; the `end` row the outcome and the gains the board has after the put back. Write to board adds a row per set to the last run's log.
  - `results.csv`: one row per setpoint (Ku, Pu, relay step and swing, KP, TI, the changes, the fit K, L and tau, the check's overshoot, reversals, t63, t90, back-off and sag).
  - `sets.csv`, the three PID table sets; `write-to-board.txt`, the lines Write to board sends, to paste into PuTTY if wanted; `relay_<mbar>mbar.csv` and `check_<mbar>mbar_<n>_up.csv` / `_back.csv`, each relay test's and check step's samples; a check step's file has the predicted pressure and valve beside the measured ones (`p_predicted_mbar`, `valve_predicted_pct`, empty with no fit). A check that a refinement replaced (or that was undone) is deleted, so only the check each result came from is kept (the session log still has every sample).
  - `autotune-learned.csv` beside the run folders: the learned gains and fit per setpoint (above).

So an autotune that is stopped, stalls, loses the link or is cut short by closing the GUI keeps everything up to there. The run bar says which step it ended in and what it was doing.

Download session CSV (Logger box) gives the samples since the GUI started, up to 4 hours, from memory.

Long logs (a weekend): the GUI's memory does not grow (the page keeps 4 hours, the event log 200 lines) and the logger file grows about 0.3 MB an hour, so 70 hours is one file of about 20 MB and 250,000 rows, which Excel opens. What stops a log is the PC sleeping. On Windows the GUI asks the PC not to sleep on its own while it runs (`--allow-sleep` turns that off); the screen can still turn off. Closing the lid, Sleep from the Start menu or a Windows Update restart still stop it, so keep the laptop plugged in with the lid open and restart for any pending update before you leave. Closing the browser tab does not stop the log; closing the GUI's window does. A gap of over a minute with no samples is written to the event log with its start and end, so a gap shows on Monday.

## Run it with Python

Python 3.8 or later, standard library only. Keep `tools/pmc-gui` and `tools/gain-schedule` side by side (it imports the autotune from there), so nothing needs pip or admin rights. On Windows without admin, the "Windows embeddable package" zip from python.org runs after unzipping.

```
python pmc_gui.py <board IP>
python pmc_gui.py <board IP> --ls336 <336 IP>
```

Then open the address it prints, normally http://localhost:8080. If Windows refuses 8080 (WinError 10013: the port is in a block Windows reserves for Hyper-V, WSL or Docker) or another program has it, the GUI tries the next ports and prints the one it got. `--port 8090` picks a page port yourself.

The 336 can also be connected from the page (Live tab, Lake Shore 336: its IP, then Connect). Its inputs default to `A=Heat exchanger, D=Cold head`; give others as `--ls-inputs A "B=Sample" D`, or in the Inputs box. The 336 needs Ethernet on (Interface menu) with an address on the PC's subnet. `tools/lakeshore/ls336_log.py` logs the 336 alone, without the GUI.

## Before you start

- Menu > System > Remote control On, or every button answers ERR 211.
- If the board's link drops, the page says so in the top bar and reconnects every 2 s by itself. An autotune waits up to 2 minutes for the link to come back (the run bar says Waiting) and then carries on; after that it stops and says so. The board itself carries on in the mode it was in (a run that stops mid-step leaves the valve in MANUAL where it was).
- The board takes one text-port connection at a time, and a new one replaces the old. Close PuTTY first. The 336 logger can run alongside: it is a separate connection to a separate instrument.
- STOP on the page and on the screen both end AUTO.
- A fault (F-) ends an autotune run, since the board refuses AUTO and valve moves until it is reset: reset it on the Board tab and start the run again with the setpoints left. A warning that drops the board to MANUAL (W-2, W-4, W-5) skips that setpoint only.
- Every Set and save that changes a gain is written to flash, and so is every PID SET the autotune sends (it sends one when the gains differ). Set gains when they change, not in a loop.

To try it without the board, run `node simulator/tests/tcp-board.js` and use `127.0.0.1` as the address. Its flow line is the bench cryostat fitted to the bench logs, so an autotune there sees roughly the bench's gains, periods, creep and needle stick; a speed above 1 (the second argument) shortens the cryostat's times but not the GUI's 1 s samples, so run an autotune at speed 1.
